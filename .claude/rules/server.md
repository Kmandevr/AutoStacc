# Store API

- One folder per area in `server/` (auth, catalog, cart, checkout, payments, orders, entitlements, downloads, storage, email, admin, analytics, stats, impersonation, audit, account, projects, polls, dev; shared `lib/`). A module owns its tables and exports a `routes` table; `server/app.js` only wires them. Put code in the module that owns the data it changes; call another module through its exported functions, never its SQL. A file past ~150 lines or doing two jobs gets split. Map and flows: [docs/store.md](../../docs/store.md).
- `functions/` holds only thin Pages Function entry points. No logic there.
- Never trust the browser: prices, totals, titles, ownership, order and payment status come from D1 or a verified provider event. Ownership reads `entitlements` only, never orders. Validate every input with `lib/http.js` helpers (`readJson`, `str`, `id`, `int`, `email`) and answer with `fail(status, code, message)`.
- Not-yours looks like not-there: other people's orders, unpublished products and admin routes answer 404. No messages that reveal whether an email has an account.
- Payment outcomes change orders only through `payments/events.js` (once per event id, must match the order, compare-and-set transitions). Grants are idempotent (`grantStmt`, unique per product/source/email). Anything a retry can repeat must be safe to repeat.
- Passwords, sessions and resets are Better Auth's (`auth/index.js`). Never write password, session or token crypto; `lib/crypto.js` is Web Crypto HMAC/SHA-256 only.
- Secrets come from `env` via `lib/config.js` (add new ones there with a production check). Never log secrets, keys, tokens, card data or full emails in errors sent to the browser.
- SQL: bound parameters only (`?`), never string-built values. Money in integer cents, times as ISO UTC text, ids from `newId(prefix)`.
- Schema changes are new forward-only files in `db/migrations/` (never drop or rewrite data). `db/catalog.sql` is generated by `scripts/build.js` (products, projects, polls); don't edit it.
- Platform features (follows, Auto-Stacc, polls, Pac tags on files) sit on top of the store: they may grant only through `entitlements/grants.js` and never change how downloads are authorized (per product). A feature a project can opt out of checks `usesFeature(project, "<feature>")` and answers 404 when it's off.
- Admin changes go to the audit log (`audit(app, "area.verb", ...)` from `audit/log.js`), never with secrets or customer emails. A new state-changing route is refused during a support impersonation unless it opts in with `{ impersonation: "allow" }` (or `"test-payments"`); opt in only for what a support check needs (docs/admin.md).
- Each file starts with a `//` (or `--` for SQL, `#` for TOML) comment saying what it is for. A new route gets tests in `test/api/` (see `.claude/rules/tests.md`).
