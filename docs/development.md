# Development

## Run it

```sh
npm install            # once: Wrangler (local Cloudflare), Better Auth, Stripe SDK
npm run dev            # site + store API on http://localhost:8788  (node scripts/dev.js [--port N] [--fresh])
node scripts/serve.js  # static pages only, store "offline" (what the SEO and verify-site checks use)
```

`npm run dev` builds (`scripts/build.js`), collects `dist/` (`scripts/dist.js`: the static pages, `guide/`, the creators' folders and the root files, `speculation-rules.json` among them; `/shop/<id>`, `/product`, `/events` and every project's release and event pages go to the Function), creates `.dev.vars` with fresh local secrets if missing, applies migrations to a local D1 database, syncs the first-party creators, projects and polls (`db/catalog.sql`), seeds test data and starts `wrangler pages dev`. Nothing touches Cloudflare. Local state lives in `.wrangler/state` (`--fresh` wipes it).

Test mode (local only):

- **Payments:** the mock provider. Checkout opens `/checkout?...&mock=...` with buttons: pay, decline, abandon. They go through the same pipeline as Stripe events.
- **Email:** kept in the database. Read verification and reset links at `http://localhost:8788/api/dev/outbox?to=<email>`.
- **Catalog:** there are no products in `data/` (the code-based catalog is retired, #176). The six test products (`sample-pack-vol1`, `serum-presets`, ...), the `frayed-signals` Stacclet with its four Pacs and one fixture event (2099-06-01) come from `test/support/catalog-fixtures.js`, seeded by `scripts/dev.js` after `db/catalog.sql`. Every product is for sale, plus `dev-free`, `dev-paused` and `dev-unpublished`, and each product has a small test file to download. The first-party release (`hail`) is re-seeded from migration 0040 after the catalog, because locally the migrations run before the project exists. The news post `hail-out-now` is seeded too and stays hidden (#174). A second project (`dev-other`) and test polls (open, closed, and one on that project) are seeded too.
- **Admin:** sign up as `admin@autostacc.test` (in `.dev.vars` `ADMIN_EMAILS`), confirm via the outbox, open `/admin`.
- **First-party owner:** sign up as `owner@autostacc.test` (`.dev.vars` `FIRST_PARTY_OWNERS=autostacc=owner@autostacc.test`, added to an older `.dev.vars` too), confirm it, open `/studio`: that account becomes `autostacc`'s owner (#172). The test suites use the same account.

## Environment variables

Plain settings are `[vars]` in `wrangler.toml` (per environment: top level = local, `env.preview`, `env.production`); secrets are `.dev.vars` locally and Pages secrets in production ([store-setup](store-setup.md)). Validated by `server/lib/config.js`.

| Name | Kind | Meaning |
| --- | --- | --- |
| `APP_ENV` | var | `development`, `test`, `preview` or `production` |
| `SITE_URL` | var | The site's own address (links in mail, Stripe return URLs, origin checks) |
| `PAYMENT_PROVIDER` | var | `stripe`, or `mock` (development/test only) |
| `EMAIL_PROVIDER` | var | `brevo`, or `log` (not in production) |
| `EMAIL_FROM` | var | `Name <address>` of a Brevo-verified sender for purchase mail (`store@`) |
| `EMAIL_FROM_NOREPLY` | var | the same for automated mail: account, password reset, alerts (`noreply@`) |
| `BETTER_AUTH_SECRET` | secret | 32+ chars, signs sessions |
| `DOWNLOAD_SIGNING_SECRET` | secret | 32+ chars, different, signs download links |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | secret | Stripe keys (`sk_live_` only in production, never elsewhere) |
| `STRIPE_MARKETPLACE_KEY`, `STRIPE_MARKETPLACE_WEBHOOK_SECRET`, `PLATFORM_COUNTRY` | secret, optional | The second Stripe account for creators' sales and payouts; off without the key, which needs the webhook secret beside it; `PLATFORM_COUNTRY` defaults to `US` ([payouts-setup](payouts-setup.md)) |
| `STRIPE_MARKETPLACE_TAX` | optional | `off` switches Stripe Tax off on creators' checkouts (testing only; the deploy doesn't set it) |
| `BREVO_API_KEY` | secret | Brevo key |
| `BREVO_NEWS_LIST` | secret, optional | The Brevo list id that accounts with "AutoStacc news" switched on are kept in (so news can also be sent from Brevo); without it the Control Center's News tab still sends |
| `BREVO_NEWSLETTER_LISTS` | secret, optional | Each project's Brevo newsletter list, `project-id:list-id` comma-separated (`glitches-and-stitches:3`); a project without one says "coming soon". Development and tests treat every project as open and contact nobody |
| `ADMIN_EMAILS` | secret | Admin emails, comma-separated (optional: `role = admin` in the user table works too) |
| `FIRST_PARTY_OWNERS` | secret, optional | `<creator>=<email>` pairs, comma-separated: the verified account that owns each first-party creator in the Studio (#172; [store-setup](store-setup.md)) |
| `FEATURES_OFF` | var, optional | Comma-separated feature switches to turn off in this deployment without a code change (`packs.builder`, `packs.suggestions`, `packs.editor`, `packs.analysis`, `downloads.bundles`, `library.collections`, `store.derivedFacets`, `product.contentsTree`, and the default-off `downloads.deflate` and `auth.adminTwoFactor`; `server/lib/features.js`). A switched-off feature's routes answer 404 |
| `FEATURES_ON` | var, optional | Comma-separated switches that are off by default to turn on (production and preview set `community.forum`, the open community, owner 2026-10-21; others: `downloads.deflate`, `auth.adminTwoFactor`: admins' two-step sign-in, [store](store.md#accounts)); `FEATURES_OFF` wins |
| `SWEEP_TOKEN` | secret, optional | 32+ chars. The engine Worker's daily cron sends it to `POST /api/internal/sweep` to run the retention sweep ([packs](packs.md)); the same GitHub secret goes to the store and the engine Worker. Without it the sweep is off |
| `STRIPE_API_BASE` | var | Tests only: points the Stripe SDK at the fake Stripe server (ignored outside development/test) |
| `ENGINE_URL` | var, optional | Development and tests only: the Pack Builder sends jobs straight to this engine service (`test/mock-engine/server.js`, or the real binary: `R2_ENDPOINT=http://localhost:8788/api/internal/engine-storage R2_BUCKETS=autostacc-files engine/target/release/autostacc-engine serve 127.0.0.1:8095`) instead of the queue; the engine reads and writes the local `FILES` bucket through the store's stand-in relay (`server/packs/engine-storage.js`). Ignored in production |

Bindings: `DB` (D1), `FILES` (private R2), `PREVIEWS` (R2 for preview clips), and in production `JOBS` (the queue `autostacc-engine-jobs`, read by the engine Worker; [engine](engine.md)).

## Database

Schema changes are new files in `db/migrations/` with the next number after the highest (today `0060_community_tags.sql`, so `0061_....sql`; there is no `0010`), forward-only: add tables and columns, never drop or rewrite data in a migration. Apply locally by restarting `npm run dev`; the deploy applies them to production before publishing. `db/catalog.sql` is generated; never edit it.

CI: `.github/workflows/store.yml` (unit and API tests in one job, browser tests in another; pull requests only, a newer push cancelling the run it replaces, and a job skipped when it already passed on exactly these files (a fingerprint of every file but the notes, kept as a marker in the Actions cache); skipped on pull requests that change only `docs/`, `.claude/` or `*.md`); the merge to `main` doesn't run them again, and the deploy runs the unit tests before publishing.

When fixing a store bug, write the failing test first in the suite for that area.

Groups run in parallel, so each starts its own stores on its own ports with its own state folder (`.wrangler/test-<kind>-<group>`); tests inside a group run in order and may build on each other (the `features` browser tests reuse the admin account the impersonation test creates). A new API suite goes into the group whose stores it needs; a new browser test into the group it belongs to.

## Keeping docs true

Each note in `docs/` names the code it describes in its `covers:` frontmatter. `node scripts/docs-test.js` (in CI's `seo.yml` and `release-check`) fails on broken facts in the notes, README, CLAUDE.md and `.claude/` docs (frontmatter, links, named repo paths, `npm run` scripts, `covers:` entries, the vault index, store settings no note mentions) and warns about notes whose covered code changed on the branch while the note didn't (a FAIL with `--strict`, which CI uses on pull requests except Dependabot's: update the note, or re-check it and bump `updated:`), and about code areas no note covers. It also fails when `README.md` doesn't name a top-level page or folder, a workflow, an npm script or a data file; the README's `covers:` list is the HTML comment on its first line, so it goes stale like a note. The Stop hook script (`.claude/hooks/docs-reminder.sh`) asks Claude once to check those notes before finishing; it is registered under `Stop` in `.claude/settings.json` (the owner switched it on on 2026-10-15). A new note or code area gets its `covers:` line in the same change. Closed issues lose their status labels (`.github/workflows/clear-status-on-close.yml`).

**Security tooling.** CodeQL (`.github/workflows/codeql.yml`) scans the JavaScript and the workflows on pull requests that change code and weekly, with the `security-extended` queries; it runs only once the repository is public (free there; private repositories would need GitHub's paid security add-on). Dependabot (`.github/dependabot.yml`) opens one grouped pull request a month per ecosystem (npm at the root and in `workers/engine/`, Rust in `engine/` and `engine/fuzz/`, the workflows' actions); security fixes come as soon as GitHub knows of them once Dependabot security updates are on in the repository's settings. `npm audit` and `cargo audit` (in `engine/`) check the same by hand. How to report a vulnerability: `SECURITY.md`. The code is published to be read, not reused: `LICENSE` (all rights reserved). Because the repository is public: the deploy jobs (`deploy.yml`, the engine's `deploy` in `engine.yml`) use the `production` Environment, so their secrets can be kept there and limited to `main`; dependency install steps run with the Cloudflare and engine tokens blanked; deploy logs blank any address in a mail failure; a fuzz crash is uploaded only while the repository is private; `.github/CODEOWNERS` names the owner for CI, the store API, the engine, scripts and the Claude instructions (enforced once the `main` ruleset requires code-owner review); and the `tasks` skill treats only the owner's and collaborators' issue text as instructions. What must stay private never goes in issues, pull requests, commit messages or logs: security problems go to a draft security advisory (the issue forms link to it, and they warn that issues are public), and other private work only to the owner, never into the repository (there is no private tracker) (the `tasks` skill, "What stays private"). The deploy log names resources but never their ids, and counts failed emails without their reasons.

## Extending

- **New product type:** one entry in `data/product-types.js`.
- **New payment provider:** a file in `server/payments/` with `name`, `livemode`, `createCheckout`, `retrieveCheckout`, `refund` (and webhook verification producing the normalized event), plus one line in `server/payments/index.js` and its webhook route. Orders already store `provider`.
- **New email provider:** one function in `server/email/providers.js`. **New email:** one template in `server/email/templates.js`, sent with `sendEmail(app, kind, to, data, { dedupeKey })` (the key is claimed before sending, so it goes once even from two requests at once).
- **New entitlement source** (bundle, subscription): grant with `grantStmt` and a new `source_type` (add it to the CHECK in a migration).
- **New API route:** add it to the owning module's `routes` table; a new module adds one import and one entry in `server/app.js`.
