# Store discovery

The store page (`/shop`) is a search over the real catalog in D1, with filters, sorting and pages answered by the server, plus curated rows ranked for the visitor. Everything a product claims comes from its own data; nothing (reviews, sales, compatibility) is invented to fill a label. The owner's choices behind it: [decisions](decisions.md) (2026-10-09, "Store recommendations stay on the visitor's device").

## Metadata

- **Vocabulary:** `server/discovery/vocabulary.js` is the one list of structured fields (facets) and allowed values: genre, style, mood, energy, made for (`use`), contents, file format, DAW, plugin, key, system (`os`), level (`skill`), plus BPM ranges and specs (sample rate, bit depth). Synonyms fold creators' words into one value (`dnb` → Drum & Bass, `one-shot` → One-shots); unknown words are refused, never stored. `data/vocabulary.js` is its browser copy, generated by `scripts/build.js` (a unit test keeps them equal). The same file holds the asset vocabulary (`FORMATS`, `KINDS` with old names as `KIND_SYNONYMS`, `MIDI_ROLES`, `INSTRUMENTS`) shared by the processing engine, Your Stacc (`data/content-types.js` is generated from it) and the store's contents-derived filters (below; [packs](packs.md)). It also gives the engine its words for suggestions (`engineVocabulary()`, with `INSTRUMENT_SYNONYMS` and `MIDI_ROLE_WORDS`), checks what a creator may set on a file in the Pack Builder (`assetValueOk`), and the browser copy carries instruments and MIDI roles for the review screen.
- **Per kind:** `SCHEMAS` says which facets mean something for each kind of product (the keys of `data/product-types.js`; site templates from the community library have style only): BPM for sample packs, stems and music but not visuals; plugins for presets and VJ loops but not sample packs. A filter only appears where it applies; a value for a field that doesn't apply is refused.
- **Storage:** `product_facets` (one row per product, facet, value; migration `0012`), plus `bpm_min`/`bpm_max`, `released_at` and `search_text` on `products`. Every product gets them (the code-based catalog that set them from data/products.js was retired, #176) from the creator's "Store details" (`js/studio-details.js`), checked again on the server (`server/creators/products.js`). Derived scores never live with the product's data.
- **From the files (Phase 7):** when a Pac version is published, `server/discovery/contents.js` works out what the product's published files contain from their published details (`product_files.meta`; an unpublished version never counts): kinds (as `contents`), file formats, DAW and plugin (from the format), keys, instruments, sample rates and bit depths, and the tempo range. The totals go to `product_contents` (migration `0020`; a table of its own, from when a catalog sync rewrote catalog products' columns on every deploy), and the values into `product_facets` with `origin = 'derived'` (switch `store.derivedFacets`), so filters, search and recommendations find a product when at least one file matches. Instrument, sample rate and bit depth are derived-only facets (`DERIVED_FACETS`): no kind lists them, so nobody sets them by hand, and the store offers them wherever a product has them. A creator's own rows (`origin = 'creator'`) are kept apart: the Studio form reads and writes only those (`facetsOf(..., { creatorOnly })`), a value both have is the creator's, and a derived value comes back when the creator drops it (`restoreDerivedStmt`). The BPM filter and the product page use the creator's range, else the files' (`product_contents.bpm_min/max`). Contents are worked out again whenever a publish, or an admin rejecting or pulling a Pack Builder file, changes what is delivered; a failed refresh never fails the publish, and the daily sweep (`sweepContents`) catches up any product whose files changed since, and makes the derived rows follow the switch: switched off, the files' tempo range stops counting at once and the derived values leave at the next sweep; switched on again, the sweep restores them. Recommendations count instruments in the taste score (`TASTE_FACETS.instrument`, 0.4).
- **Held files** (a copyright takedown, [copyright](copyright.md)) leave both the derived contents and the contents tree.
- **What's inside:** `GET /api/products/:id/contents` (`contents-routes.js`, switch `product.contentsTree`; published, visible products only, 60 s public cache) lists the Pack Builder files' folders, names, kinds, formats and sizes with the totals, never a link, key or hash; `js/product-contents.js` shows it on product pages (`[data-product-contents]`), hidden for products without such files. It also returns the Pacs' public preview clips (`previews`, up to three per Pac) and the read me's text (`readme`); the page plays the clips above the folders (`<audio controls preload="none">`, each titled) and folds the read me under **Read me** as escaped plain text, each only when present. Search timing with 3,000 products stayed within a few percent of before (`test/api/discovery.test.js` timings).
- **Suggestions:** the Studio shows values a product's own title, description and tags mention (`suggestFacets`); the creator ticks them or not. Nothing is applied automatically.

## Search API

`GET /api/store/search` (public, cached 60 s): `q`, `category`, any facet (`genre=house,techno`), `creator` (project ids), `price_min`/`price_max` (dollars), `free=1|0`, `sale=1`, `new=1` (released or added in the last 30 days), `bpm_min`/`bpm_max`, `sort` (relevance, bestselling, newest, price-asc, price-desc, discount, name), `page`, `per` (up to 48).

- **Semantics:** OR within a group, AND between groups. A tempo filter needs a stated tempo (products without one drop out while it's set); every other missing detail only matters when that detail is filtered. Malformed input is a 400 (`invalid_filter`); a well-formed value the vocabulary doesn't know (an old link) is dropped and listed in `ignored`.
- **Prices:** every statement reads products through one CTE that applies running sales exactly like `server/promotions` `salePrice` (the minimum charge included), so the price filtered, sorted and shown is the price checkout charges. "On sale" and "discount" are only true while a sale runs.
- **Counts:** each facet group is counted with every other filter applied but not itself (so its other values stay reachable); categories, creators, price and BPM ranges and the toggles likewise. One `db.batch`; lists go in as one JSON parameter (`json_each`), far below D1's parameter limit.
- **Best-selling:** active purchase entitlements in the last 90 days (refunds revoke them; carts and wishlists never count). Cards show only a floor bucket ("5+ bought recently", 10+, 25+...), never an exact number, and nothing under 5.
- **Search:** words match `search_text` (title, description, tags, facet labels, maker); a title hit ranks higher. `LIKE` over a few thousand rows is fast enough today (see Limits).
- `GET /api/store/suggest?q=` (autocomplete: matching facet values with counts, creators, product titles), `GET /api/store/similar/:id` (non-personal look-alikes for a product page).
- Ownership is never in these answers: cards ask `/api/products/state` (the one place that decides "owned"), so a product you own never shows as unowned.

## Recommendations

`POST /api/store/recommendations` (never cached). The browser sends a summary of its own history (`js/taste.js` `profile()`); the server adds what the account holds (confirmed purchases; the wishlist while personal picks are on), then:

1. **Eligibility first, in SQL:** visible, not paused, within the visitor's stated limits (`constraints`: the same parameters as search, e.g. a price ceiling or `daw=ableton-live`), and not owned, dismissed or in the cart. Up to 400 candidates: most sold (60%), newest (20%) and a random slice (20%), so new products get a chance in a large catalog.
2. **Score** (`server/discovery/rank.js`, weights in `server/discovery/weights.js`): the weighted mean of components that are each 0..1, so raw counts, prices and percentages are never added together:

| Component | Weight | How it is normalized |
| --- | --- | --- |
| preference | 0.30 | Per taste facet (genre, style, mood, use, energy, contents, instrument, kind) the best match among the product's values, each facet weighted; a facet the product doesn't state counts 0.3 (neutral), not 0 |
| search | 0.20 | Share of the recent search words found (title hit 1, elsewhere 0.5) |
| behavior | 0.18 | Similarity to the closest product engaged with, times how much that engagement says |
| price | 0.07 | 1 − (log-price distance from the middle of explored prices) / 2; 0 without price history |
| quality | 0.05 | half the creator (1 verified, 0.5 otherwise), half buyers' stars as a confidence-adjusted average (`RATING`: the mean pulled toward 3.5 as if it had 5 more reviews; none sits at 3.5), scaled 1..5 → 0..1 |
| popularity | 0.08 | log(1 + 3·purchases + 2·saves + 0.1·views), divided by the catalog's highest |
| freshness | 0.05 | Linear from 1 (today) to 0 (60 days) |
| discovery | 0.07 | 0.5 outside the visitor's usual kinds and genres + 0.3 if seldom viewed + 0.2 × a daily rotation per device |

   Then: × (1 − 0.12 per time shown and passed over, at most −50%), × (1 − 0.5 × likeness to a dismissed product), × 0.75 for something already opened, carted or saved.
3. **Evidence weights** (`EVIDENCE`): save or explicit choice 1, cart 0.7, preview 0.5, owned 0.4, opened from a list 0.25, product page view 0.15, filter 0.3, dismissed −0.6. Repeats count less each time. A view is weak evidence; a purchase shapes taste but the product itself is never offered again.
4. **Diversify and build sections:** at most 2 products per creator (project) in a section, each further one from the same creator or genre worth less; each product at most once across sections; a section with fewer than 2 products is left out. Sections: Recommended for you (only with some history), Popular in your genres, Similar to your favorites (with saved, carted or owned products), Bestselling (3+ confirmed purchases in 90 days), Deals matching your interests / On sale now, Recently added, Free and worth trying, Discover something different.

The current search and filters always win: while the store is narrowed, the sections step aside and results are ordered only by the chosen sort. Recommendation generation takes tens of milliseconds locally on a 3,000-product catalog (`test/api/discovery.suite.js` prints the timings).

## History, privacy and control

- **On device only:** `js/taste.js` keeps one event log in `localStorage` (`gs:taste:v2`) with one schema `{ t, id?, facet?, value?, q?, at }` for view, click, preview, cart, wishlist/unwishlist, dismiss, search, filter and impression. Policy: a view of the same product within 30 minutes or an impression on the same day isn't counted again; events older than 90 days and beyond 400 are dropped; purchases are never inferred (the server knows confirmed ones).
- **Sent, not kept:** the summary travels with each recommendation request and is used for that answer only: not stored, logged or linked to the account. "Forget my history" clears it; "Turn off personal picks" clears it and stops recording (everyone then sees the same rows). /privacy says so.
- **Wishlists** (`server/wishlist/`, `wishlist_items`): signed-in only, visible products only, up to 500; each person reads and changes only their own; deleted with the account and part of the data export. Others see only aggregate counts (popularity).

## Pages

- `/shop`: `js/store-browse.js` (state in the address, results, chips, pages, the filter drawer on phones; offline it shows an empty state with the offline note, since every product lives in the store), `js/store-filters.js` (panel and chip templates), `js/store-suggest.js` (combobox), results and rows draw store-style card sizes (`GS.productCard` with `mixed`: featured banners, artwork capsules; [modules](modules.md)), `js/store-sections.js` (rows, tune picks, not interested, your wishlist; on the home page `data-sections="2" data-brief` keeps two rows and the same controls, [browse](browse.md)), `js/wishlist.js` (hearts), `css/store.css` (on phones the filter drawer is frosted glass over a blurred page).
- Product pages: every stated detail in "Details", a wishlist button, and "You might also like" (`js/similar.js`).
- Other pages' grids (`js/shop.js`) stay simple: featured or a project's products, each opening its own page.
- Loading (2026-10-21): the first load of `/shop` fills the grid with 12 placeholder cards and the rows with one placeholder row, and product pages' Contents, Reviews and "You might also like" show placeholders while they load (and hide again if empty), all through `GS.skeleton` ([modules](modules.md#shared-helpers-every-feature-uses)). Later searches and filters keep the old results dimmed under `aria-busy` (`css/store.css`, which never dims the placeholders themselves), so the grid doesn't flash.

## Limits and next steps

- **Ratings from buyers' reviews** ([store](store.md), `server/reviews/`, #96): the search CTE adds each product's shown reviews (owners only, not hidden: `RATINGS_SQL`), their average and the confidence-adjusted score. **Top rated** (`sort=rating`) orders by that score, so one 5-star review doesn't outrank four averaging 4.5; `rating_min=1..5` keeps products averaging at least that (none without reviews), with the "4 stars and up" count in `toggles.rated`; cards show `★ average (n reviews)` only when there are reviews. Creators' replies aren't built (not decided).
- **Search is `LIKE` over `search_text`:** fine for thousands of products; move to D1's FTS5 if the catalog or latency grows (issue #97).
- **Signals are cached 60 s per Worker instance;** best-selling counts are read live.
- **No code-defined products:** the placeholders were deleted (#173) and every product, AutoStacc's own included, is a Studio product, so the store shows only what creators publish.
